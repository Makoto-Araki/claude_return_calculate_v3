部品 `$ARGUMENTS` を TDD で実装する。仕様と規約は CLAUDE.md（特に「認証とレート制限」）に従う。

エンドポイント（add / subtract / multiply / divide）は `/tdd` で進める。このスキルは、HTTP の入出力だけでは観測できない部品や、複数のエンドポイントに横断してかかる機能を対象とする。

## 部品の一覧

| 部品 | 内容 | テスト | 実装 | テストの水準 |
| ---- | ---- | ------ | ---- | ------------ |
| `auth` | 設定ファイルの読み込み、`X-API-Key` の検証、401 | `tests/unit/test_auth.py` | `app/auth.py` | 設定の読み込みは単体、401 は `TestClient` |
| `rate-counter` | 時計を注入できる、ユーザーごとの固定ウィンドウのカウンター | `tests/unit/test_rate_counter.py` | `app/rate_counter.py` | 単体（HTTP を通さない） |
| `rate-limit` | `app/rate_counter.py` のカウンターを使った依存関係、429、`Retry-After`、処理順序 | `tests/unit/test_rate_limit.py` | `app/rate_limit.py`（新規）、`app/main.py` | `TestClient` |

テストと実装のファイル名は、1 対 1 に対応させる（`app/<名前>.py` と `tests/unit/test_<名前>.py`）。

## 前提の確認

- `$ARGUMENTS` が `auth`、`rate-counter`、`rate-limit` のいずれかであること。そうでなければ、作業を始めず、ユーザーに確認する。
- 対象のテストや実装がすでにある場合は、上書きしてよいかをユーザーに確認する。
- 依存する部品が済んでいること。`rate-counter` と `rate-limit` は `auth` の後、`rate-limit` は `rate-counter` の後に進める（`app/auth.py`、`app/rate_counter.py` の有無で確認する）。済んでいなければ、作業を始めず、ユーザーに確認する。
- エージェントは別のエージェントを呼べないため、この手順はメインのセッションが順番に呼び出して進める。
- コミット、プッシュ、PR 作成は行わない（CLAUDE.md の Git 運用）。変更は作業ツリーに残す。

## 手順

1. **Red**: `test-agent` を呼び、上の表のテストに失敗するテストを書かせる。
   - 渡す内容: 部品名、CLAUDE.md「認証とレート制限」の該当部分、テストの水準、`tests/` 以外は編集しないこと、既存のテストの構成（fixture、parametrize、命名、docstring）に合わせること。
   - 部品ごとの追加の指示は、下の「部品ごとの注意」を渡す。
   - 報告から確認する: 追加したテスト一覧、失敗の理由が実装がないこと（import エラー、404 など）であること、仕様解釈で迷った点。
   - テストの件数が報告と食い違う場合は、`uv run pytest <テストファイル> --collect-only -q` で数え直す。
2. **Green**: `implement-agent` を呼び、テストを通す実装を `app/` に書かせる。
   - 渡す内容: 部品名、`tests/` は編集しないこと、既存の `app/` の書き方に合わせること、部品ごとの注意。
   - 報告から確認する: 作成・変更したファイル、`pytest`（tests/unit/ 全体）、`ruff check`、`ruff format --check`、`mypy` がすべて通過していること。
3. **レビュー**: `review-agent` を呼び、テストと実装をレビューさせる。
   - 渡す内容: 対象のテストと実装のパス、CLAUDE.md の仕様とコーディング規約（docstring を含む）に照らすこと、「認証とレート制限」の観点（review-agent の定義にある）を重点的に見ること、ファイルを編集しないこと。
4. **判定**:
   - 承認なら、完了の報告に進む。
   - 「要修正」なら、指摘ごとの差し戻し先（test-agent または implement-agent）に、指摘の内容を渡して修正させ、手順3に戻る。
   - 任意の軽微な指摘は、修正するかをユーザーに確認する。

## 部品ごとの注意

### auth

- 実際の設定ファイル（`config/users.toml`）を読まない。ダミーのキーを使った設定を、テストごとに注入する（`tmp_path` と環境変数 `USERS_CONFIG_PATH`、または依存関係の差し替え）。
- 設定の読み込みの異常（ファイルなし、形式不正、`name` や `api_key` の重複）が、起動時のエラーになること。
- 401 の観点: ヘッダーなし、キーが違う、空のキー、前後に空白のあるキー。ヘッダーなしとキー違いが同じ本文であること。
- 認証に成功した場合は、既存のエンドポイントがこれまでどおりの結果を返すこと。
- 既存のエンドポイントのテスト（`test_add.py` など）は、認証を入れると、すべて 401 になる。これは仕様変更なので、各テストの `client` fixture が、有効なダミーのキーを `X-API-Key` に付けるよう直してよい。ただし、既存のテストの検証内容（期待値、観点）は削除も緩和もしない。fixture の変更は、全テストファイルで同じ形にそろえる。
- 認証が本番の設定ファイルに依存して、テストが外部の状態で通ったり落ちたりしないこと。

### rate-counter

- 時計は、テストから差し替えられる形にする（現在時刻を返す関数や、オブジェクトを引数で受け取る）。`time.sleep` で実時間を待たない。
- 観点: 60 回目までは許可、61 回目は拒否、ウィンドウが切り替わると 1 回目から数え直す、ユーザーごとに独立、残り秒数（`Retry-After` 用）の計算（切り上げ、最小 1）、古いウィンドウのカウントを残さない。
- 境界: ウィンドウの最初の瞬間と最後の瞬間（例: 時刻が 59.999 秒と 60.0 秒）。
- 排他制御: 複数スレッドから同時に呼んでも、カウントがずれないこと（例: 100 スレッドから呼んで、許可が 60 回ちょうど）。
- テストごとに、カウントの状態が独立していること（共有のグローバルな状態を残さない）。

### rate-limit

- 時計とカウンターは、テストから差し替えられること。実時間を待たない。
- 観点: 60 回までは 200、61 回目は 429（本文 `{"detail": "Rate limit exceeded"}`）、`Retry-After` ヘッダーが残り秒数、次のウィンドウで再び 200、ユーザーごとに独立、4つのエンドポイントすべてに効く、1 回として数える（重みなし）。
- 処理順序: 未認証で `a=0` を送ると 401、認証済みで枠超過のときに `a=0` を送ると 429、認証済みで枠内のときに `a=0` を送ると 422。
- 認証に成功したリクエストは 422 になる場合も数える。認証に失敗したリクエストは数えない（401 を繰り返しても、他のユーザーの枠を消費しない）。
- 429 の本文に、キーや内部情報が出ないこと。

## 中止の条件

次のいずれかなら、作業を止めて報告する。

- レビューを3周しても承認されない。
- 同じ指摘が2周続いた。
- テストが誤っている、または仕様と食い違っていると implement-agent が報告した。
- 仕様が曖昧で、test-agent が質問を返した。

中止の報告には、部品名、各周の指摘の要約、未解決の指摘、考えられる原因を含める。

## 完了の報告

- 部品名と、レビューを何周で承認されたか。
- Red、Green、レビューの各フェーズの結果（テスト件数、検証コマンドの結果）。
- 未対応の任意の指摘。
- 次の作業の案（ブランチを切ってコミット・プッシュ・PR 作成。ユーザーの指示があるまで行わない）。
